    Groundline — Architecture¶

    Status: Draft (aligned with REQUIREMENTS.md)
    Owner: GYANESH
    Last updated: 2025-11-06

    This document describes the logical and physical architecture of Groundline: a git-hosted corpus of Markdown, a local RAG index and services, and assistant-agnostic clients (HTTP, MCP, CLI). Normative behaviour, schemas, and phases remain in REQUIREMENTS; this file is the systems view for implementers and reviewers.

    1. Goals and constraints¶

    Goal How the architecture supports it
    Single source of truth Markdown + YAML front matter in git; PR merges only (REQUIREMENTS §4).
    Compounding knowledge Full corpus at a commit SHA drives the index; each merge extends coverage (§1, §3).
    Grounded agent use Retrieve → mandatory rerank → context packs → citations on any generation path (§5.5–§5.7, §5.10).
    No vendor lock-in Canonical REST + JSON on loopback; optional MCP mirroring the same operations (§5.9, §5.12).
    Local-first Index and models run on the developer machine by default; optional CI validates corpus (§5.2, §7–§8, §12).

    Non-goals for architecture v1: Mandatory cloud embedding, proprietary-only IDE APIs, or storing work-tracker exports in the corpus (§3).

    2. System context (C4-style)¶

    flowchart LR
  subgraph contributors [Contributors]
    Dev[Developers / QE / PM / DM]

  subgraph git_host [Git host]
    Repo[(Groundline repo)]
  end

  subgraph local [Contributor machine]
    Corpus[knowledge/*.md + meta]
    Pipeline[Index pipeline]
    Store[(Vector + optional sparse index)]
    API[Local HTTP API]
    MCP[MCP stdio python -m ki mcp]
    Manifest[.rag manifest gitignored]
  end

  subgraph clients [Clients]
    IDE[IDE assistants]
    Term[Terminal / scripts]
  end

  Dev -->|PR merge| Repo
  Dev -->|clone / pull| Corpus
  Corpus --> Pipeline
  Pipeline --> Store
  Pipeline --> Manifest
  API --> Store
  MCP -->|HTTP tools| API
  IDE -->|localhost REST| API
  IDE -->|MCP host| MCP
  Term -->|curl / CLI| API
  Repo -->|same files| Corpus

    Responsibility split:

    • Git remote: Version history, review, branch protection — not the runtime for retrieval.
    • Local runtime: Build index from working tree or pinned commit, serve queries with health (index_status, sync_status) (§5.6, §12.1–§12.2).

    3. Repository layout (information architecture)¶

    High-level map (§6):

    knowledge/
  technical/      # architecture, runbooks, ADRs
  delivery/       # curated delivery summaries, analysis
  testing/        # QE-led quality knowledge
  functional/     # product / glossary / features
  meta/           # golden queries, policies, templates (paths may vary)
scripts/          # indexer, API server, validators (when implemented)
meta/             # contribution templates, author-profile.example.yaml, etc.
.rag/             # generated index + manifest (gitignored)

    Front matter carries title, area, type, status, author_role, and domain derived from path or validated against it (§6.1 Domain inference).

    4. Logical components¶

    Component Responsibility
    Corpus Authoritative Markdown under knowledge/; evolves by PR.
    Ingest Discover files, parse front matter, normalize body.
    Chunker Structure-aware splits; stable chunk ids; metadata propagation (§5.4).
    Embedder (MVP) tf‑idf word vectors per chunk (dense surrogate until neural embeddings); model id in manifest.
    Sparse index (MVP) Okapi BM25 over chunk term frequencies — hybrid with dense, fused via RRF (§5.5, §5.11).
    Retriever First stage: hybrid RRF → candidate set (e.g. top 20–40).
    Reranker Mandatory second stage; local cross-encoder or light ranker (§5.5).
    Context assembler Caps per doc, related: expansion, inclusion_reason, optional diversification (§5.10).
    API REST JSON: retrieve, context_pack, health, optional get_chunk / neighbours (§5.6).
    MCP adapter Optional stdio server (python3 -m ki mcp after pip install -e ".[mcp]"): tools teamkm_* call the same local HTTP API; agent loop stays in the host (§5.9, §5.12; MCP.md).
    Validator scripts/validate_frontmatter.py: schema + path/domain rules (§6.1, §8).
    Sync (optional) Fetch + fast-forward only when safe; feeds staleness for reindex (§12.2).

    5. Index build data flow¶

    flowchart TD
  A[knowledge/**/*.md] --> B[Parse front matter]
  B --> C[Strip / attach doc metadata to chunks]
  C --> D[Structure-aware chunking]
  D --> E[tf-idf vectors per chunk]
  D --> F[BM25 stats per chunk]
  E --> G[.rag/index.staging]
  F --> G
  G --> H[Atomic rename to .rag/index]
  H --> I[manifest.json after success]

    Incremental build: Content-hash per file; re-chunk/re-embed only changed files (§5.5). Fingerprint: Align index staleness with git tree / hashes (§12.1).

    6. Query / context-pack data flow¶

    sequenceDiagram
  participant Client as Client (IDE / script)
  participant API as Local API
  participant R as Retriever
  participant RR as Reranker
  participant A as Context assembler

  Client->>API: query + optional filters (area, domain, profile)
  API->>R: hybrid or dense (phase-dependent)
  R-->>API: candidates N
  API->>RR: query + passages
  RR-->>API: scored reorder
  API->>A: top passages + limits
  A-->>API: context pack (grouped, inclusion_reason)
  API-->>Client: JSON + citations

    Contract: Responses expose paths, line ranges, retrieval and rerank scores where applicable (§5.6). Downstream generation must cite chunks or mark gaps (§5.7).

    Index freshness and golden eval (implemented)¶

    Surface Role
    python3 -m ki --root . status CLI report: manifest corpus_fingerprint vs live corpus hash
    GET /v1/health index_stale, index_stale_now, corpus_fingerprint_current / _indexed
    python3 -m ki --root . eval Golden queries: recall@k + MRR@k (meta/golden_queries.yaml)
    python3 scripts/golden_queries.py Same harness as ki eval (CI uses this entrypoint)

    Re-index when stale: python3 -m ki --root . index. See TESTING.md.

    7. Contribution flow (retrieval-first)¶

    Designed so agents do not invent duplicates blindly (§5.8):

    1. Refresh index to merge base.
    2. Retrieve similar chunks for draft outline or title.
    3. Present top‑k with scores and paths.
    4. Recommend edit existing vs new file under knowledge/<domain>/....
    5. Human opens PR; CI validates front matter and optionally runs golden-query regression (§8).

    Optional: contribute --dry-run or PR bot listing related docs (§5.8, §10).

    8. Session lifecycle (developer experience)¶

    Primary trigger: coding-assistant session starts MCP or local API → background sync (if enabled) → index if missing/stale (§12.1).

    • Git hooks are supplementary; they do not run on server-side clone (§12.1 caveat).
    • Auto-sync: Fast-forward only when working tree is clean; block on dirty/diverged (§12.2).

    9. Security and compliance (architecture-relevant)¶

    Topic Approach
    Secrets / PII Out of corpus; pre-merge checks recommended (§3, §7).
    Network Default loopback binding; optional LAN with documented risk (§5.9).
    Model policy Embedding/reranker documented in meta/; air-gap teams use local models (§5.3, §7).
    Audit Citations + inclusion reasons for traceability (§5.7, §5.10).

    10. Phase alignment (build order)¶

    Phase Architecture emphasis
    MVP Dense index, mandatory rerank, context packs with caps + related, citations, HTTP + optional MCP, health + fingerprint (§10).
    V1+ Hybrid retrieval, MMMR/hardening, richer expansion, OpenAPI (§5.11, §10).
    V2 Optional PR bot, published index artefacts (§10).

    Tracked in REQUIREMENTS §9: vector store, embedding/reranker models, chunk defaults, API port/versioning, hook vs MCP-only automation, etc.
